# Development and Engine Architecture

Native Apple Silicon download manager built with SwiftUI, SwiftData and a separately downloaded Aria2 Next engine.

## Build and test

- Xcode 27, Swift 6 language mode (tested with Swift 6.4).
- macOS deployment target: 26.5. SDK: the installed macOS SDK, currently 27.0.
- The helper is arm64 only. There are no Swift Package Manager or CocoaPods dependencies.

Open `ChopChop.xcodeproj`, or run:

```sh
Scripts/verify.sh           # Shared CI / pre-release gate; automatically cleans its temporary directory
Scripts/check.sh unit       # Unit and RPC regression tests
Scripts/check.sh release-unit # Optimized unit tests with test-only injection enabled
Scripts/check.sh ui         # UI tests; requires an unlocked desktop
Scripts/check.sh all        # Both suites
Scripts/check.sh release    # Release build
python3 Scripts/smoke-aria2-next.py
```

`check.sh` honors `DEVELOPER_DIR` and otherwise finds full Xcode, including when `xcode-select` points to Command Line Tools. Focused local checks use ad-hoc signing and produce `DerivedData/`; set `CHOPCHOP_DERIVED_DATA` to change the location. Additional arguments are passed to `xcodebuild`. Current GitHub DMGs retain ad-hoc signing; Developer ID signing and notarization remain deferred.

`release-unit` enables testability and debugger injection and disables hardened runtime only for that ad-hoc test invocation. `release` keeps hardened runtime and the distribution configuration's injection restriction. Run test suites sequentially: hosted unit tests and UI tests launch the same application identifier.

The Python smoke test downloads a pinned official engine into temporary storage, verifies its SHA-256, and then uses a loopback HTTP server and temporary files. It checks real engine downloads, pause, restart with the original GID and saved progress, final SHA-256, same-name file protection and clean shutdown. It re-signs a **temporary copy** of the helper for standalone execution; the opt-in integration tests verify the downloaded engine inside the app sandbox. No engine executable is tracked in the current source tree or included in build products.

## Engine startup and installation

At launch ChopChop checks for a usable managed engine, generates and persists a secure RPC token if needed, and starts the engine automatically. Existing token and download-folder settings are preserved. The sidebar shows checking, installation, startup, running, and failure states. Tracker and ED2K network maintenance runs after startup instead of delaying it.

A missing engine opens a required installation sheet with **Download and Start**, retry on failure, and quit. Installation is automatic into the app's own data directory:

```text
~/Library/Containers/com.conight.ChopChop/Data/Library/Application Support/ChopChop/Engines/<installation UUID>/aria2-next
```

There is no folder chooser. The embedded `EngineInstaller.xpc` service downloads only an official stable Apple Silicon release, verifies SHA-256, applies sandbox inheritance signing, and writes a fresh installation folder. The parent app verifies that the engine executes inside its sandbox before atomically recording the active installation. Failed attempts do not replace the existing installation or modify the signed `.app` bundle. The active managed installation is the only engine used; there is no embedded fallback.

The private installer runs on demand without App Sandbox; the main app and running engine remain sandboxed. It checks the caller against the containing app's code-signing requirement, accepts only canonical release versions and the app's own `ChopChop/Engines` folder, and requires no administrator privileges. Directory access is shared with an implicit URL bookmark. This follows Apple's [XPC service separation](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingXPCServices.html) and [cross-process bookmark](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox) mechanisms.

A background GitHub check runs on each app launch. Newer stable releases appear as `2.8.5 → 2.8.6` in the sidebar's Engine row, without a startup alert. The whole Engine/Status area always opens ChopChop's Engine settings, including when no update is available or Settings was previously showing another pane. Offline or rate-limited checks never block a usable local engine.

A compact `↑ New` badge appears at the lower right of the Engine area while an update is available, and hides during installation or once updated. Its subtle tint follows the system accent color; the text, arrow, tooltip, and accessibility hint also convey the update without relying on color. It supports light/dark appearances, increased contrast, and reduced transparency, following Apple's [color guidance](https://developer.apple.com/design/human-interface-guidelines/color). The status row keeps a stable height and shows a concise state, with the running process ID available in its tooltip when no update is pending.

Engine settings offers a manual check and an **Update to …** button with progress and retryable inline errors. The current engine keeps running while the new binary downloads and verifies. ChopChop then saves the session, stops the engine, snapshots its session/recovery state, and starts the replacement. Only successful RPC startup commits the new installation; a failed replacement restores the previous engine and runtime state. An intentionally stopped engine stays stopped. Quitting cancels an in-progress update. Updating never opens a browser or asks for a destination folder.

Engine installation and updates use a native linear progress bar in a consistent location, following Apple's [progress indicators](https://developer.apple.com/design/human-interface-guidelines/progress-indicators) and [feedback](https://developer.apple.com/design/human-interface-guidelines/feedback) guidance. A session-level download delegate reports measured bytes, total size, percentage and speed over XPC. Unknown totals and verification/restart stages stay indeterminate; there is no invented overall percentage. The sidebar mirrors progress. Cancel is available before the current engine is stopped; a retry starts the download again. Failure feedback names the stage, preserves the installed version and offers an inline retry.

App Sandbox does not automatically permit executing a new binary in Application Support. The app includes a narrowly scoped read-only [home-relative path exception](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/AppSandboxTemporaryExceptionEntitlements.html) for its own container's `ChopChop/Engines/` directory. The macOS sandbox grants execution for that specific exception; the app and helper retain App Sandbox and Hardened Runtime. Without it, a normal Release app can read the downloaded file but `Process.run()` misleadingly reports that it does not exist. XCTest's additional execution permissions can conceal this failure.

After building Release, run `Scripts/verify-engine-installation.sh /path/to/Release/ChopChop.app` to test the actual Release entitlements without XCTest or UI interaction. The probe downloads and runs a verified engine in the production installation directory, then removes only its new staging folder. It never activates the engine, changes the installed-engine manifest, or interrupts the running engine. The script signs an isolated copy with the built app's entitlements and Hardened Runtime.

For a real installation and RPC verification without UI automation:

```sh
TEST_RUNNER_CHOPCHOP_TEST_ENGINE_DOWNLOAD=1 Scripts/check.sh unit \
  -only-testing:ChopChopTests/ManagedEngineTests/testAutomaticInstallAndRPCStartupInsideSandbox \
  -only-testing:ChopChopTests/ManagedEngineTests/testManualUpgradeFrom285ThroughSandboxedStore
```

These opt-in tests download official engines into isolated test storage and verify authenticated RPC from the sandboxed host. They cover both first installation and a real 2.8.5-to-latest manual update through the application store. The default unit suite tests startup, token persistence, required installation/retry, offline checking, update reminders, release/checksum validation, installer boundary checks, and cancellation without a network download.

## Updating the download engine

The application resolves the latest stable release from the official upstream repository when installing or checking for updates. Its version display comes only from the verified managed installation; an empty installation shows “Unavailable”. App builds do not download or pin an engine version.

`Scripts/engine-test-release.json` pins an upstream version and SHA-256 **only for the CLI smoke test**. Update this metadata when adopting a new integration-test baseline, then run `python3 Scripts/smoke-aria2-next.py`. The executable is fetched into a temporary directory and removed at the end of the test. The engine's libraries (including libcurl, OpenSSL and libtorrent) remain part of the upstream executable.

`Scripts/verify-release-app.py` rejects an embedded engine or a bundled-engine version key. The release workflow publishes only the DMG and its checksum; it does not download or mirror engine source.

## Persistent data and recovery

Production data stays in the app sandbox's Application Support directory:

- `ChopChop/aria2.session`: unfinished tasks and their GIDs.
- `ChopChop/aria2.log`: engine diagnostics.
- `aria2-next/`: engine recovery databases and protocol state.

Keep the session and recovery state together. Aria2 Next 2.8.3 and later require matching task recovery records for stream resume; adding the same URL as a new task is not a substitute for restoring its original session. Existing files follow the engine's collision policy. See the [upstream migration note](https://github.com/AnInsomniacy/aria2-next/releases/tag/v2.8.3).

On the first engine launch after a version change, ChopChop copies any nonempty existing session into `ChopChop/Session Backups/` before the engine can rewrite it and shows the backup location. HTTP tasks migrated from 2.4.9 may restart from zero; their old partial files are preserved. The backup retains the original task list for rollback with the old engine. Normal 2.8.6-to-2.8.6 restart recovery is covered by the smoke test.

To repeat the legacy migration check with a saved 2.4.9 helper, run `python3 Scripts/smoke-aria2-next.py --previous-engine /path/to/old/aria2-next`. It verifies that the migrated task keeps its GID, completes under a new filename and leaves the old partial's bytes unchanged.

Automation uses in-memory settings and per-process temporary engine state. Development machine settings under `.codex/`, Xcode user state and build outputs are ignored by Git.

## Download history and paused restoration

SwiftData now adds `PersistentDownloadRecord` alongside the existing settings models. `DownloadHistoryStore` keeps sanitized task snapshots keyed by GID and deletion tombstones; it merges engine observations without changing original addition dates. Imported tasks use a clearly labeled first-recorded date. Finished records survive engine purges, and unavailable unfinished records expose their last saved progress without pretending they are still transferring. Clearing history never deletes payload files. Tombstones contain only GIDs and prevent delayed polls or reconnection from resurrecting cleared records; matching engine tasks are removed on the next successful reconciliation.

The engine starts with `--pause=true`, before loading its existing session and native recovery databases. New additions explicitly override `pause=false`, while local torrent selection retains its initial pause. A restored magnet awaiting file selection reopens the selection sheet for its existing GID; cancelling that sheet keeps the paused task. BT tasks enable `force-save` because the engine considers active seeders finished when serializing a session. Once seeding has ended, a completed torrent result is durably archived in SwiftData before removing its stopped engine result and saving the session; this prevents a completed force-saved torrent from returning on restart. Failed and media recovery records stay owned by the engine. A hard crash retains validated checkpoints; bytes since the last native checkpoint may need to transfer again.

Task mutations save the engine session before waiting for polling. Partial batch submissions keep successful GIDs/history and leave only the remaining links in the editor. Poll results carry session and mutation revisions, so an older asynchronous response cannot reverse a newer change. Repeated RPC failures become inline connection feedback with automatic retry, while saved history remains visible.

`EngineTaskSnapshot` maps RPC data separately from the transport. The shared progress model uses bytes for ordinary downloads and native `media` duration for finite HLS/DASH tasks. Unknown sizes, metadata, verification, live recording, and remux finalization do not invent percentages. `getVersion` supplies the running version and capabilities. Unsupported FTP is rejected, including FTP hidden inside Thunder links; SFTP is identified independently.

History does not duplicate request headers, cookies, authorization, signed query URLs, peer lists, or tracker credentials. A source with URL credentials, query parameters or a fragment is omitted from persistent history. Error text is redacted. Editing a failed task opens a fresh draft; it does not remove the original task or claim to resume its native recovery state. Authentication may need to be entered again.

Regression coverage includes additive migration from a settings-only store, durable history, offline tombstones, stale polls, partial batches, inline reconnection, capability gating, media phases, and credential redaction. The isolated CLI smoke test verifies normal restart and abrupt termination with active, waiting, paused, and seeding tasks, retaining GIDs and validated progress and checking no HTTP requests occur before manual resume. No UI automation is required.

Reliability validation on 2026-10-07: 175 unit/RPC tests, 171 passed and 4 opt-in cases skipped (three live installer tests and one design render). The real 2.8.6 HTTP/BT smoke test passed, including abrupt termination, paused recovery, original GIDs, payload checksums, and seeding. The hardened Release build passed the release verifier for architecture, signatures, entitlements, notices, and absence of an embedded engine. No UI automation was run.

## Native imports and completion notifications

`DownloadImportReader` normalizes links, validates enabled types and reads selected Torrent/Metalink documents while holding their original security-scoped URL. Documents stay in memory until their confirmation sheet is dismissed; nothing copies them into the app bundle or persists their embedded request credentials. Imports are bounded to 100 resources, 16 MiB per document and 32 MiB of documents per incoming batch. Failures appear inline alongside the valid inputs. Local documents are reviewed individually; Metalink contents are sent to `aria2.addMetalink`, which can return multiple task IDs. Local Torrent contents enter the existing paused file-selection flow through `aria2.addTorrent`.

AppKit open-URL events, SwiftUI drops, clipboard paste and File → Open Download File… share this reader and the `DownloadInputCoordinator`. Cold-launch events wait for engine setup. One window owns the global add draft at a time; external imports wait while a manual draft is open, and dismissal restores the manual draft before presenting the next item. Menu-bar add requests survive a closed download window. `Info.plist` registers Magnet/ED2K schemes and imported Torrent/Metalink UTIs with document handler rank `Alternate`; the app does not programmatically replace default handlers. URL and document events only prepare drafts—RPC submission still requires confirmation.

`DownloadNotificationCoordinator` uses UserNotifications through an injectable delivery interface. Notifications default off and request alert permission only from the explicit General setting. Delivery checks the current system authorization and suppresses alerts while the app is active. The first engine snapshot silently consumes old completions, except newly submitted tasks known to the current run. Subsequent completion transitions are grouped per refresh; torrent metadata and media finalization are excluded, while finished torrent payloads can notify at the start of seeding. A defaulted SwiftData `completionObserved` flag is saved before delivery so repeated polls and restarts do not replay alerts. Foreground/disabled/denied completions are consumed silently, without delayed bursts. Notification payloads contain task IDs and redacted names, without source links, paths or request headers; clicking one selects its task in All Downloads.

The hosted test environment uses a silent notification backend and never requests real permission or delivers OS notifications. Regression tests cover mixed imports, original document bytes after source removal, size limits, disabled types, item providers, cold-launch queuing, sheet ownership and draft restoration, handler declarations, Metalink/Torrent RPC methods, opt-in permission, baseline suppression, batching, disk persistence and notification navigation. The CLI smoke test also verifies a two-file Metalink against loopback HTTP and paused Torrent submission. Finder routing and system notification banners are intentionally not exercised by UI automation.

Native-import validation on 2026-10-08: 195 unit/RPC tests, 191 passed and 4 opt-in cases skipped. The real 2.8.6 smoke test passed for two-file Metalink import, HTTP downloads, original-GID recovery after normal and abrupt termination, and paused Torrent/seeding recovery. The hardened Release app passed architecture, signatures, entitlements, notices and no-embedded-engine verification. No user-input automation, real notification delivery, publication or installed-app replacement was performed; temporary build/test artifacts were removed after validation.

Apple references: [Opening URL resources](https://developer.apple.com/documentation/appkit/nsapplicationdelegate/application(_:open:)), [declaring file types](https://developer.apple.com/documentation/uniformtypeidentifiers/defining-file-and-data-types-for-your-app), and [requesting notification permission](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications).

## Media, browser integration, and download tools (2026-10-08)

`MediaDownloadCoordinator` owns the inspection lifecycle. Recognized HLS/DASH manifests (or an explicit source mode) are submitted with `media-pause-after-probe=true`; the engine discovers opaque track IDs and pauses before payload transfer. Confirming changes the options and unpauses the same GID. Cancelling removes only a newly owned inspection task; reopening an existing paused inspection preserves it. Generation checks reject stale completions. Track selection validates media kind, live/VOD time settings and muxed audio compatibility. Finishing a live recording and retrying failed media use native `finishMedia`/`retryMedia` calls. Sources, credentials and headers remain subject to history sanitization.

`Scripts/smoke-media.py` generates loopback HLS and DASH with ffmpeg, uses the pinned official test engine, checks that inspection transfers no segments, selects a lower-quality track, restarts with the original paused GID, and decodes the resulting MP4/MKV with ffmpeg/ffprobe. A growing live playlist tests pause/finish, and a controlled 403 tests authenticated same-GID media retry. ffmpeg is a test dependency only. This is direct manifest support, not arbitrary website resolution, DRM bypass or transcoding.

`BrowserCaptureServer` uses Network.framework, binds only to `127.0.0.1`, and starts only after opt-in. The import-only HTTP endpoint requires the exact loopback Host and a 256-bit pairing token; website origins, malformed/framed/pipelined requests, oversized headers/bodies and excess connections are rejected. It has connection deadlines and an import rate limit. There is no RPC forwarding endpoint. Tokens can be rotated. Browser messages enter the shared confirmation coordinator and never directly start downloads. The bundled MV3 Chrome/Edge package uses activeTab, user-triggered scripting, context menus and local storage; it requests no cookies or broad remote host access. Tests cover the parser and an actual NWListener/URLSession request as well as extension logic and manifest permissions. Browser-store publication, Safari packaging and live browser UI testing are outside this change.

`DownloadPlanning.swift` separates daily bandwidth policy, queue positioning and planning UI. `tellWaiting` positions are measured before filtering hidden engine entries, so `changePosition` uses actual queue indices. Drag data has its own exported UTI rather than plain-text GIDs. Queue changes save the engine session. Scheduled dates are optional history fields; the armed set exists only in memory and clears on engine/app startup. Explicit scheduling pauses first and saves before arming. Cancellation invalidates in-flight schedule saves. Manual pause/resume actions cancel the corresponding schedule; Pause All also cancels disabled historical dates. Due starts use the original GID and disarm before attempting RPC. Failures appear inline and do not produce recurring alerts. Bandwidth windows support midnight crossings, restore global limits outside the window and never start tasks. ChopChop must be running.

`BitTorrentManagement.swift` maps native `bt-file-priority` values (off/normal/high/top), `select-file`, `force-sequential`, preview-piece priority and per-task seed limits. Applying settings preserves the task and saves its session. Skipping every file is rejected; Pause is the explicit all-transfer stop. The inspector reports native peers/seeds/availability and tracker RPC observations without inventing announce success. Tracker observations refresh on demand. Reannounce and native piece recheck are explicit actions.

`DownloadConnectionRepair` replaces only the supplied auth headers, keeps other request headers and rejects newline injection. Paused HTTP/media tasks resume after the update; failed media uses `retryMedia`. A new URI is accepted only for a paused, single-file HTTP task with zero completed bytes and the same origin. Media presentation changes, cross-origin changes and files with partial data require a separate task. We cannot infer file identity from a name or size. HTTP terminal results do not have a native retry method; Edit and Add Again remains the explicit new-task route.

`FileDigest` streams 1 MiB chunks with CryptoKit off the main actor, supports cancellation, and checks size/modification metadata before and after hashing. It opens regular files without blocking on FIFOs and rejects changing files. SHA-256/SHA-512 are preferred; MD5/SHA-1 remain available for older published checksums. Digests are not persisted. Permission failures can be resolved with a user-driven file chooser. No file content is modified or uploaded.

`MacIntegration.swift` provides App Intents for link confirmation, pausing, and counts-only summaries. App initialization registers the existing store; intents do not create another engine or bypass import confirmation. Xcode extracts `Metadata.appintents` into the app. The Dock uses NSDockTile and a native progress bar, excludes paused/offline/seeding tasks, and omits a percentage when any included task has unknown progress. Known ordinary downloads use byte weighting; mixed media uses the mean task fraction. Completed files use SwiftUI ShareLink. Incoming system sharing can be composed with the Add Download Links action in Shortcuts; there is no standalone Share extension target.

## Public beta preparation (2026-10-08)

### Shared verification gate

`Scripts/verify.sh` is the entry point for CI and release preparation. It validates both String Catalogs, runs extension tests and the English Swift suite, checks Chinese offscreen geometry, runs the isolated real HTTP/RPC and HLS/DASH suites, then builds and verifies the hardened Release app. `--package OUTPUT_DIRECTORY DMG_NAME` additionally creates and verifies a mounted DMG. This command does not publish anything.

The tested tools are Python 3.14.8, Node 24.15.0, and FFmpeg/FFprobe 9.0.2, declared in `Scripts/verification-tools.json`. Install those versions before running locally. The script prefers `python3.14`, falls back to `python3`, and accepts an explicit `PYTHON` path; version checks run before building. The GitHub composite action installs fixed Node/Python versions and a checksum-verified FFmpeg formula/bottle from a fixed Homebrew commit. Shared library dependencies are resolved by Homebrew. The engine fixture and packaging dependencies remain version- and hash-pinned separately. Updating a tool baseline requires updating these pins and rerunning both real engine suites.

By default the gate owns one temporary root containing DerivedData, CLI fixtures and DMG staging, and removes it on success or failure. `CHOPCHOP_VALIDATION_ROOT` retains an explicitly supplied directory for investigation; its owner must remove it afterwards. `cleanup-verification.py` removes only sandbox automation folders identified by test-host PIDs in that root's logs and unregisters its temporary apps from Launch Services. It never searches for or deletes installed applications or production data. Packaging outputs in the requested output directory are intentionally retained.

```sh
# Full validation, no publication and no installed-app replacement:
Scripts/verify.sh

# Validate a tagged build and retain only its distribution artifacts:
CHOPCHOP_RELEASE_VERSION=v0.0.1-beta.1 Scripts/verify.sh \
```

### Application updates and feedback

`AppVersion`, `GitHubAppReleaseClient` and `AppUpdateCoordinator` are independent of engine installation and `DownloadStore`. Release builds embed `ChopChopReleaseVersion`, including the complete prerelease tag. Untagged builds identify themselves as development builds and disable automatic checks. The Releases list, not `/latest`, supplies public candidates. Numeric prerelease components compare semantically (`beta.2 < beta.10 < stable`); stable installations exclude prereleases, and beta installations include both. Drafts, invalid tags, empty or unready assets, and releases without the expected arm64 DMG are rejected. The current request covers up to 100 public release records; pagination beyond that window is not implemented.

Automatic checks run on launch/activation, at most once per 24 hours, with the last attempt persisted even after failure. They can be disabled. ## Live transfer telemetry (2026-10-08)

`TransferDetails.swift` owns nonpersistent piece/peer/server DTOs and the cancellable, generation-checked detail monitor. The inspector polls every two seconds only while the Network tab/window is active, backing off on errors without alerts. Closing/switching cancels the observation; late results cannot replace another task's data. Pause/terminal status overrides cached peer rates and connections, and a status recheck handles finishing between `tellStatus` and `getServers`.

`PieceMap` decodes high-bit-first hexadecimal bitfields, ignores trailing spare bits and distinguishes missing/truncated data from incomplete pieces. It bounds input and renders a 240-bin overview plus 256 individually hit-tested pieces per page, with text, shape, native tooltips and keyboard/VoiceOver adjustment. `totalLength` is the *selected* BT length: v1 final-piece sizing uses the sum of **all** file lengths only when it matches `numPieces`/`pieceLength`. v2/hybrid or inconsistent spans show a nominal upper bound including padding. No file-byte or percentage inference is used to invent piece completion. BT `query_pieces` runs about every five seconds upstream, while ordinary status can update sooner.

`getPeers` supplies genuine client/state/progress, TCP/uTP, encryption/direction, source, slot/interested flags, transferred bytes and upload/download rates. `getServers` has a significant implementation limitation: the 2.8.6 libcurl branch returns **one aggregate server entry** at `group->calculateStat().downloadSpeed`. Supporting genuinely independent HTTP connection telemetry requires an upstream RPC extension. Only sanitized scheme/host/port and numeric rates leave the server DTO mapping.

Per-task `max-upload-limit` applies with `changeOption` and `saveSession`, without pause/unpause/restart. Zero means unlimited; effective global limits are read with `getGlobalOption` and refreshable in the panel. Existing global/scheduled limits and seeding policies are preserved.
